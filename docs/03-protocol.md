# 03. Протокол: свой язык поверх сокета

Файл: `src/shared/protocol.ts`. Его импортируют и клиент, и сервер.

WebSocket передаёт строки. Что в них — решаете вы. Набор договорённостей «что значит
каждое сообщение» называется **прикладным протоколом**. Без него получается россыпь
`if (data.type === …)` по всему коду, которая ломается от первой опечатки.

## Кадр

Каждое сообщение — JSON с полем `t` (type):

```json
{ "t": "ping", "ts": 1791888736761 }
```

По `t` получатель понимает, что внутри. В TypeScript это размеченное объединение
(discriminated union): после `if (frame.t === 'event')` редактор знает остальные поля.

### Клиент → сервер

| `t` | Поля | Смысл |
| --- | --- | --- |
| `hello` | `v`, `token`, `channels`, `resume` | первый кадр: версия протокола, кто я, на что подписан, что видел последним |
| `sub` | `id`, `channel` | подписаться на канал |
| `unsub` | `id`, `channel` | отписаться |
| `req` | `id`, `method`, `params` | попросить что-то сделать |
| `ping` | `ts` | «ты жив?» |

### Сервер → клиент

| `t` | Поля | Смысл |
| --- | --- | --- |
| `welcome` | `sessionId`, `user`, `epoch`, `seq`, `resumed` | сессия создана |
| `event` | `seq`, `channel`, `type`, `data`, `at` | что-то произошло |
| `ack` | `id`, `ok`, `result` \| `error` | ответ на `sub` / `unsub` / `req` |
| `pong` | `ts`, `seq` | ответ на ping |
| `error` | `code`, `message` | кадр не понят |

## Разговор целиком

```
клиент                                   сервер
  │ ── (TCP + HTTP Upgrade) ─────────────▶ │
  │ ── hello {token, channels:[orders]} ─▶ │  проверил токен
  │ ◀─ welcome {sessionId:s1, seq:41} ──── │
  │ ── ping {ts} ────────────────────────▶ │
  │ ◀─ pong {ts, seq:41} ───────────────── │
  │                                        │  ← кто-то сменил статус заказа
  │ ◀─ event {seq:42, order.updated} ───── │
  │ ── sub {id:a1, channel:order:o_15} ──▶ │  открыли карточку заказа
  │ ◀─ ack {id:a1, ok:true} ────────────── │
  │ ◀─ event {seq:null, presence} ──────── │  текущее состояние канала
  │ ── req {id:r1, note.add, params} ────▶ │
  │ ◀─ ack {id:r1, ok:true, result} ────── │
  │ ◀─ event {seq:43, note.added} ──────── │  её получат все в канале
```

Это можно увидеть вживую — в журнале на экране «Соединение».

## Почему авторизация — сообщением, а не в адресе

У `new WebSocket()` нельзя задать заголовки. Остаются три пути:

| Способ | Минус |
| --- | --- |
| `wss://host/ws?token=…` | адрес попадает в журналы сервера, прокси, историю — токен утекает |
| cookie | нужна проверка `Origin`, иначе чужой сайт подключится от имени пользователя |
| **первым сообщением** (`hello`) | соединение некоторое время «анонимное» — сервер должен закрыть его, если `hello` не пришёл |

Здесь третий путь. Сервер заводит таймер на 5 секунд (`helloTimeout` в `hub.ts`) и до
`hello` не выполняет ничего, кроме `hello`.

## Каналы

Канал — тема подписки. Клиент получает события только своих каналов.

| Канал | Что в нём | Кто слушает |
| --- | --- | --- |
| `orders` | заказы созданы и изменены | весь интерфейс (счётчик в меню, списки) |
| `notifications` | уведомления | «колокольчик» |
| `metrics` | живые цифры | только дашборд |
| `products` | остатки | экраны товаров |
| `order:<id>` | заметки и присутствие одного заказа | карточка этого заказа |

Все каналы идут через **одно** соединение — это называется мультиплексирование. Подписки
меняются по ходу работы: откройте экран «Соединение», походите по страницам и следите за
блоком «Каналы» и кадрами `sub` / `unsub`.

Здесь же место для проверки прав: «может ли этот пользователь слушать этот канал» (в демо
всем можно всё — см. комментарий в `Hub.subscribe`).

## Факты и состояния

Самое важное различие в файле.

| | Факт | Состояние |
| --- | --- | --- |
| Пример | «заказ создан», «статус изменён», «заметка добавлена» | «онлайн 42 человека», «заказ смотрят Анна и Борис» |
| Потерять можно? | **нет**: в интерфейсе останутся старые данные | да: следующее значение всё исправит |
| Номер `seq` | есть | `null` |
| Хранится для досылки | да, в буфере | нет |
| При подписке | — | сервер сразу шлёт текущее значение |

Список событий-состояний — `EPHEMERAL` в `protocol.ts`. От этого зависит всё в главе 05:
досылать после обрыва нужно только факты. Слать «историю» метрик за время обрыва
бессмысленно и дорого.

## Запрос-ответ поверх сокета

Сокет — поток сообщений без пар «вопрос-ответ». Пару делаем сами через `id`:

```json
→ { "t": "req", "id": "mv6l-7", "method": "note.add", "params": { "orderId": "o_15", "text": "…", "clientId": "…" } }
← { "t": "ack", "id": "mv6l-7", "ok": true, "result": { "note": { … } } }
```

Клиент хранит `Map<id, {resolve, reject, timer}>` и превращает это в Promise:

```ts
const { note } = await realtime.request('note.add', { orderId, text, clientId })
```

Типы параметров и результата выводятся из таблицы `Requests` — вызвать несуществующий
метод или передать не те поля не даст TypeScript.

**Когда запрос по сокету, а когда по HTTP?** В «Прилавке» почти все изменения — HTTP
(смена статуса, товары): у HTTP готовые коды ошибок, повторы, кэш, его видно в DevTools.
По сокету идут заметки и присутствие — то, что по природе «разговор». Правило: по
умолчанию HTTP, сокет — когда нужна мгновенность или запрос неотделим от потока событий.

## Проверка данных (zod)

TypeScript проверяет код, но не данные: `JSON.parse` вернёт что угодно, и `as Frame`
ничего не проверит. Поэтому на границе с сетью — схема:

```ts
const frame = decode(clientFrame, raw)     // null — мусор
if (!frame) return send({ t: 'error', code: 'bad_frame', … })
```

- **Сервер** проверяет всё строго: кадр (`clientFrame`) и параметры каждого запроса
  (`requestParams`). Клиенту доверять нельзя — запрос можно отправить и без нашего интерфейса.
- **Клиент** проверяет форму кадра (`serverFrame`), а `data` события берёт на веру: сервер
  наш и типы общие. С чужим сервером стоит описать схему каждого события.

## Версия протокола

`hello.v` — номер версии. Сервер, который её не поддерживает, закрывает соединение кодом
4426, и клиент не пытается переподключаться — нужна новая версия страницы. Это страховка на
день, когда сервер обновят, а у человека неделю открыта старая вкладка.

## Что можно улучшить

- Двоичный формат (MessagePack, protobuf) вместо JSON — когда сообщений тысячи в секунду.
- Сжатие (`permessage-deflate`) — экономит трафик, но стоит памяти сервера на каждое соединение.
- Пакетирование: несколько событий в одном кадре.
- Готовые решения, где всё это уже есть: Socket.IO, Centrifugo, Phoenix Channels, Ably,
  Pusher, Supabase Realtime (как в «Летучке»). Свой протокол стоит писать, чтобы понять,
  что они делают, — и в небольших проектах, где зависимость не оправдана.
