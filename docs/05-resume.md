# 05. Докачка, очередь, идемпотентность

Переподключиться — половина дела. Пока связи не было 20 секунд, в магазине пришло три заказа
и у двух сменился статус. Клиент об этом не знает. Глава — про то, как узнать.

## Простое решение и почему его мало

«После переподключения перезапросить всё по HTTP». Работает, и для маленьких приложений
этого достаточно. Минусы:

- каждый чих сети — десяток запросов от каждого клиента (а после деплоя — от всех разом);
- между «перезапросил» и «начал слушать» есть зазор, в который событие может провалиться.

Лучше: **сервер досылает пропущенное**, а полный перезапрос остаётся запасным вариантом.

## Закладка: номер события

Сервер нумерует факты подряд: 1, 2, 3… (`seq` в `hub.ts`). Клиент помнит номер последнего
полученного — это закладка. При переподключении называет её:

```json
→ { "t": "hello", …, "channels": ["orders"], "resume": { "epoch": "k3f9a2", "seq": 41 } }
```

Сервер хранит последние 500 фактов в буфере и отвечает:

```json
← { "t": "welcome", …, "seq": 44, "resumed": true }
← { "t": "event", "seq": 42, … }
← { "t": "event", "seq": 44, … }      ← 43 был в канале, на который клиент не подписан
```

### Когда досылка невозможна

| Ситуация | Что отвечает сервер |
| --- | --- |
| пропущенное лежит в буфере | `resumed: true` + события |
| клиент ничего не пропустил | `resumed: true`, событий нет |
| буфер уже вытеснил пропущенное (долго не было связи) | `resumed: false` |
| сервер перезапускался (другая эпоха) | `resumed: false` |

При `resumed: false` клиент вызывает `onResync()` → `queryClient.invalidateQueries()`:
весь кэш помечается устаревшим, то, что на экране, перезапрашивается (глава 07). Это тот
самый «простой вариант» — как страховка.

Условие в коде (`Hub.hello`):

```ts
const oldest = this.buffer[0]?.seq ?? this.seq + 1
const resumed = !resume || (resume.epoch === this.epoch && resume.seq <= this.seq && resume.seq >= oldest - 1)
```

`oldest - 1`: если в буфере события 8, 9, 10, а клиент видел 7 — ничего не потеряно. Видел
6 — событие 7 уже не восстановить. Граничный случай закреплён тестом.

## Эпоха

Нумерация живёт в памяти сервера и при перезапуске начинается с нуля. Событие №41 «до» и
№41 «после» — разные события. Если сравнивать только номера, клиент с закладкой 41 решит,
что ничего не пропустил.

**Эпоха** — случайный id запуска сервера. Закладка = эпоха + номер. Эпоха не совпала —
сразу `resumed: false`.

## Почему нельзя найти «дырку» по номерам

Соблазн: пришло 42, потом 44 — значит, 43 потерян? Нет: нумерация общая на все каналы, а
клиент получает только свои. Пропуски в номерах — норма.

И внутри одного соединения терять нечего: TCP доставляет всё и по порядку. Потери возможны
только **между** соединениями — а там работает закладка.

## Закладка двигается и в тишине

Если в каналах клиента час ничего не происходит, закладка стоит на месте. Тем временем
чужие каналы прокручивают буфер, и при обрыве сервер честно скажет «не могу дослать» — хотя
клиент ничего не пропустил. Лишний полный перезапрос.

Поэтому `pong` несёт текущий номер сервера, и клиент сдвигает закладку:

```ts
case 'pong': this.patch({ seq: Math.max(this.snapshot.seq ?? 0, frame.seq) })
```

Это безопасно: порядок в соединении гарантирован, значит все события с номером ≤ `seq` из
наших каналов нам уже отправлены раньше этого `pong`.

## Повторы

При досылке клиент может получить событие, которое уже видел. Защита — одна строка:

```ts
if (this.snapshot.seq !== null && frame.seq <= this.snapshot.seq) return
```

Плюс вторая линия обороны на уровне данных — версии записей (глава 07).

## Исходящие запросы: дошёл или нет?

Клиент отправил `req` — и связь оборвалась. Три возможности:

1. запрос не дошёл;
2. дошёл, выполнен, но `ack` потерялся;
3. дошёл, но сервер упал, не выполнив.

**Клиент не может их различить.** Отсюда две стратегии:

| Стратегия | Как | Риск |
| --- | --- | --- |
| at-most-once («не больше одного раза») | не повторять, сообщить об ошибке | действие могло не выполниться |
| at-least-once («хотя бы раз») | повторять до подтверждения | действие может выполниться дважды |

«Ровно один раз» на уровне сети недостижимо. Его получают сочетанием: **at-least-once +
идемпотентность**.

### Идемпотентность

Идемпотентная операция — та, которую можно повторить без вреда. «Установить статус = оплачен»
идемпотентна. «Добавить заметку» — нет: два запроса — две заметки.

Неидемпотентную делают идемпотентной **ключом**: клиент придумывает уникальный id операции
(`clientId = crypto.randomUUID()`), сервер запоминает выполненные:

```ts
const duplicate = notesByClientId.get(clientId)
if (duplicate) return { note: duplicate }     // повтор — отдаём прежний результат
```

Теперь повтор безопасен, и клиент помечает запрос `retry: true`:

```ts
realtime.request('note.add', { orderId, text, clientId }, { retry: true })
```

Что делает клиент при обрыве (`handleClose`):

| Запрос | Не был отправлен | Отправлен, ответа нет |
| --- | --- | --- |
| обычный | остаётся в очереди | **отклоняется**: «неизвестно, выполнен ли» |
| `retry: true` | остаётся в очереди | **возвращается в очередь** и уходит снова с тем же `id` |

Тот же приём у платёжных систем: заголовок `Idempotency-Key` в HTTP API.

## Очередь

Запрос, сделанный без связи, не падает сразу. Он ждёт в `pending` и уходит после `welcome`
(не после `open` — до `welcome` клиент для сервера никто):

```ts
for (const pending of this.pending.values()) if (!pending.sent) this.dispatch(pending)
```

У каждого запроса общий таймаут (по умолчанию 8 с, у заметки 15 с) — он включает ожидание
связи. Не дождались — Promise отклоняется с кодом `timeout`, заметка исчезает из списка, а
человек видит «Заметка не отправлена».

Подписки очередь не занимают: при подключении весь список каналов уходит в `hello`.

2. **«Перезапустить сервер»** — эпоха меняется, `resumed: false`, «Полных обновлений» = 1,

3. Очередь и повтор — в режиме настоящего сервера (`npm run server` + `npm run dev:real`):
   откройте заказ, остановите сервер (Ctrl+C), напишите заметку — она висит бледной,
   «отправляется…». Запустите сервер в течение 15 секунд — заметка уйдёт сама.

## Ошибки

> **Закладка — только номер, без эпохи.** После перезапуска сервера нумерация начинается
> заново, и клиент с закладкой 41 решит, что ничего не пропустил.
>
> **Искать потери по «дыркам» в номерах.** Нумерация общая на все каналы — пропуски в своих
> событиях нормальны.
>
> **Повторять неидемпотентный запрос.** «Добавить заметку» после обрыва, без ключа, — две
> заметки. Сначала ключ (`clientId`), потом `retry: true`.
>
> **Отправлять очередь при `open`, а не после `welcome`.** До рукопожатия сервер вас не знает и
> отвергнет запросы.
>
> **Закладка стоит в тишине.** В ваших каналах час тихо, буфер ушёл вперёд — после обрыва лишний
> полный перезапрос. Сдвигайте закладку по `pong`.
>
> **Нет запасного пути.** Досылка не всегда возможна: при `resumed: false` нужен полный
> перезапрос (`onResync`).

2. Почему `clientId` заметки придумывает клиент, а не сервер?
3. Запрос `presence.focus` не помечен `retry: true`. Что с ним будет, если связь оборвалась сразу
   после отправки, и почему это не страшно?
4. Что увидит человек, если заметка не дошла за 15 секунд?

<summary>Ответы</summary>

1. Видел 7 — да: `resume.seq >= oldest - 1` (7 ≥ 8 − 1), всё после 7 лежит в буфере. Видел 6 —

2. Ключ нужен **до** отправки: по нему сервер узнает повтор, а клиент — свою заметку в событии

   при новой сессии `usePresence` отправит `focus` заново (эффект зависит от `sessionId`).
4. Бледная заметка исчезнет из списка и появится тост «Заметка не отправлена».
