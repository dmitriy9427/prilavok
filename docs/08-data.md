# 08. Данные: TanStack Query

Файлы: `src/api/http.ts`, `queries.ts`, `mutations.ts`, `src/lib/query-client.ts`.

## Серверное состояние — не обычное состояние

Список заказов не принадлежит приложению: он живёт на сервере, а у нас — копия, которая
стареет. С такой копией связаны задачи, которых нет у `useState`: когда перезапросить, как
не запрашивать дважды, что показать во время загрузки, как отменить ненужный запрос.
TanStack Query решает их все. Redux или Zustand для серверных данных не нужны.

## Запрос = ключ + функция

```ts
export const orderQuery = (id: string) =>
  queryOptions({
    queryKey: ['orders', 'detail', id],
    queryFn: ({ signal }) => api<OrderDetail>(`/orders/${id}`, { signal }),
  })
```

`queryOptions` — описание, которое понимают все части приложения:

```ts
useQuery(orderQuery(id))                              // компонент
queryClient.ensureQueryData(orderQuery(id))           // загрузчик маршрута
queryClient.setQueryData(orderQuery(id).queryKey, …)  // правка кэша (типы выводятся из описания)
```

### Ключи

Ключ — адрес данных в кэше, иерархический:

```
['orders', 'list', { page: 0, status: ['new'], q: '' }]
['orders', 'detail', 'o_15']
['stats', 30]
```

- **Всё, от чего зависит ответ, — в ключе.** Забыли положить туда фильтр — два разных
  запроса получат один кэш.
- Иерархия позволяет действовать группами: `invalidateQueries({ queryKey: ['orders'] })` —
  всё про заказы; `['orders', 'list']` — только списки.
- Ключи собраны в объекте `keys` — чтобы `sync.ts` и мутации не писали их руками.

## Свежесть

```ts
defaultOptions: { queries: { staleTime: 30_000, retry: (failures, error) => … } }
```

| Понятие | Смысл |
| --- | --- |
| fresh (свежие) | в течение `staleTime` повторный показ экрана **не делает** запрос |
| stale (устаревшие) | данные показываются сразу, а в фоне идёт обновление |
| `invalidateQueries` | принудительно пометить устаревшими |
| `gcTime` | сколько держать данные, на которые никто не смотрит (5 минут по умолчанию) |

30 секунд — компромисс: переходы между экранами мгновенные, данные не слишком старые.
Главное обновляется событиями сокета, не дожидаясь устаревания.

Повторы: при сбое сети или 5xx — до двух раз. При 4xx — нет: 404 повтором не исправить.

## Состояния запроса

```tsx
const { data, error, isPending, isPlaceholderData, refetch } = useQuery(ordersQuery(search))

if (error) return <ErrorState error={error} onRetry={refetch} />
if (isPending) return <Skeleton />
if (data.rows.length === 0) return <EmptyState />
return <OrdersTable … dimmed={isPlaceholderData} />
```

Четыре состояния у каждого списка: ошибка, загрузка, пусто, данные. Пропущенное состояние —
самый частый дефект интерфейсов.

`placeholderData: keepPreviousData` — пока грузится следующая страница, показываем
предыдущую приглушённой (`isPlaceholderData`). Таблица не схлопывается в скелет на каждое
нажатие.

## Отмена

`queryFn` получает `signal` и передаёт его в `fetch`. Человек быстро печатает в поиске —
запросы на «и», «ив», «ива» отменяются, сеть не занята ответами, которые уже не нужны.

## Бесконечный список

```ts
infiniteQueryOptions({
  queryKey: ['customers', 'list', params],
  queryFn: ({ pageParam }) => api('/customers', { query: { …params, cursor: pageParam, limit: 100 } }),
  initialPageParam: 0,
  getNextPageParam: (last) => last.nextCursor,      // null — больше нет
})
```

В кэше — массив страниц; компонент склеивает их `data.pages.flatMap(p => p.rows)` и зовёт
`fetchNextPage()`, когда прокрутка подошла к концу (глава 10).

**Курсор или номер страницы?** Номер страницы прост и позволяет прыгнуть на 7-ю. Но если
во время листания в начало добавилась строка, всё сдвигается: одна строка покажется дважды.
Курсор («дай 100 после этой позиции») этому не подвержен — для лент берут его.

## Мутации

```ts
useMutation({
  mutationFn: (input) => api('/products', { method: 'POST', body: input }),
  onSuccess: (product) => {
    queryClient.setQueryData(keys.product(product.id), product)       // карточка — точно
    queryClient.invalidateQueries({ queryKey: keys.productLists })    // списки — перезапросить
  },
})
```

После изменения — два пути, как и с событиями сокета: поправить кэш точно, если знаем как,
или пометить устаревшим, если нет. Оптимистичные обновления — в [главе 07](07-cache-sync.md).

## HTTP-клиент

`api()` — одна функция поверх `fetch` (`http.ts`):

- **`fetch` не считает 404 и 500 ошибкой** — он «успешно получил ответ». Статус проверяем
  сами и бросаем `ApiError { status, code, message, fields }`.
- `fetch` бросает только когда ответа нет вовсе (сеть, CORS) → `ApiError(0, 'network')`.
- Отмену (`AbortError`) пробрасываем как есть — Query её ждёт.
- 401 → выход из аккаунта.
- `Authorization: Bearer …` добавляется в одном месте.

## Ошибки API — одного вида

```json
{ "error": { "code": "validation", "message": "Проверьте поля формы", "fields": { "sku": "Такой артикул уже есть" } } }
```

| Статус | Когда | Что делает интерфейс |
| --- | --- | --- |
| 401 | нет или плохой токен | выход, экран входа |
| 403 | нет права | тост (кнопка и так была скрыта) |
| 404 | нет такой записи | экран «не найдено» |
| 409 | версия устарела / артикул занят | тост + свежие данные / ошибка под полем |
| 422 | данные не прошли проверку | ошибки под полями формы |
| 5xx, сеть | сбой | повтор, затем «Не удалось загрузить» с кнопкой |

`code` — для программы (`if (error.code === 'version_conflict')`), `message` — для человека.
Сравнивать текст сообщения в коде нельзя: его перепишут.

## Ошибки

> **В ключе не всё, от чего зависит ответ.** `['orders']` для разных страниц и фильтров — все
> они получат один кэш. В ключе — все параметры запроса.
>
> **`fetch` в `useEffect`.** Гонки (ответ старого запроса пришёл позже нового), нет кэша, нет
> отмены, нет повторов. Ровно это и делает Query.
>
> **Не передавать `signal`.** Человек быстро листает страницы — ненужные запросы продолжают
> грузиться и тратить сеть.
>
> **Путать `isPending` и `isFetching`.** `isPending` — данных ещё нет вовсе (скелетон).
> `isFetching` — данные есть, идёт обновление в фоне (маленький индикатор). Скелетон на каждом
> фоновом обновлении — мигание.
>
> **Повторять запрос при 404.** Повтор не найдёт то, чего нет. Повторяйте только сеть и 5xx.

## Попробуйте сами

1. Почему у списка заказов `placeholderData: keepPreviousData`? Что увидит человек без этой
   строки при переходе на вторую страницу?
2. Откройте дашборд, уйдите на «Заказы» и через 10 секунд вернитесь. Будет ли запрос статистики?
   А через минуту?
3. Почему `api()` пробрасывает `AbortError` как есть, а остальные сетевые ошибки превращает в
   `ApiError(0, 'network')`?

<details>
<summary>Ответы</summary>

1. Пока грузится новая страница, показывается старая (а не пустая таблица со спиннером).
   Без неё таблица «моргала» бы пустотой на каждом переключении.
2. Через 10 секунд — нет: `staleTime` 30 с, данные свежие. Через минуту — да, при показе экрана
   они устарели и перезапрашиваются (старые видны, пока идёт запрос).
3. Отмена — не ошибка: Query сам отменил ненужный запрос и ждёт именно `AbortError`. Остальное
   приводится к одному виду ошибки, чтобы интерфейс показывал понятный текст.
</details>
