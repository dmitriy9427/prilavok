# 02. WebSocket с нуля

## Зачем он вообще

HTTP устроен как вопрос-ответ: **клиент спрашивает, сервер отвечает**. Сам сервер заговорить
не может. Для «покажи заказ №15» это идеально. Для «сообщи, когда придёт новый заказ» — нет:
клиенту пришлось бы спрашивать снова и снова.

WebSocket — **постоянное двустороннее соединение**. Открыли один раз, и дальше любая сторона
шлёт сообщения, когда захочет.

| | HTTP | WebSocket |
| --- | --- | --- |
| Кто начинает разговор | всегда клиент | любая сторона |
| Соединение | на один запрос | живёт минуты и часы |
| Накладные расходы на сообщение | заголовки (сотни байт) | 2–14 байт |
| Состояние | нет (каждый запрос независим) | есть: сервер помнит клиента |
| Кэш, CDN, повтор при сбое | есть «из коробки» | всё вручную |

Последняя строка — цена. С HTTP надёжность дают браузер и инфраструктура. С WebSocket вы
получаете трубу, а надёжность строите сами. Этому посвящены главы 03–05.

## Как соединение появляется из HTTP

WebSocket начинается с обычного GET-запроса:

```http
GET /ws HTTP/1.1
Host: localhost:8787
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Origin: http://localhost:5173
```

Сервер соглашается:

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

После `101` тот же TCP-сокет перестаёт быть HTTP и становится каналом для **кадров**
(frames). Поэтому WebSocket работает на тех же портах (80/443) и проходит через те же
прокси, что и сайт.

В Node это событие `upgrade` — см. `server/index.ts`.

Адреса: `ws://` — без шифрования, `wss://` — поверх TLS (как `https://`). Страница,
открытая по `https`, **не может** подключиться к `ws://` — браузер заблокирует. Поэтому в
`src/config.ts` схема выводится из адреса страницы: `location.origin.replace(/^http/, 'ws')`.

## API браузера — он крошечный

```js
const socket = new WebSocket('wss://example.com/ws')

socket.onopen = () => socket.send('привет')          // соединение установлено
socket.onmessage = (event) => console.log(event.data) // пришло сообщение
socket.onclose = (event) => console.log(event.code, event.reason) // закрыто
socket.onerror = () => {}                             // ошибка (без подробностей)

socket.send('строка')            // или ArrayBuffer / Blob для двоичных данных
socket.close(1000, 'пока')       // закрыть: код и причина
socket.readyState                // 0 CONNECTING · 1 OPEN · 2 CLOSING · 3 CLOSED
```

Это всё. Что важно знать сверх этого:

- **Объект одноразовый.** Закрылся — новый `new WebSocket(…)`. «Переподключить» существующий
  нельзя. Отсюда класс `ReconnectingSocket` (глава 04).
- **`onerror` бесполезен для диагностики** — браузер намеренно не сообщает подробностей
  (иначе страница могла бы сканировать чужую сеть). После `onerror` всегда приходит
  `onclose` — вся логика там.
- **`send()` до `onopen` бросает исключение**, а после закрытия — молча теряет данные.
  Поэтому обёртка проверяет состояние и возвращает `true/false`.
- **Сообщения приходят целиком и по порядку.** Это гарантия TCP + протокола: не нужно
  собирать куски и сортировать. Но гарантия действует **внутри одного соединения** — что
  было между двумя соединениями, WebSocket не знает (глава 05).
- **Нельзя задать заголовки.** `new WebSocket(url, protocols)` — и всё. `Authorization`
  не добавить. Варианты: cookie (уйдёт сама), токен в адресе (попадёт в журналы серверов —
  плохо) или токен **первым сообщением** — так сделано здесь.
- **CORS на WebSocket не действует.** Любой сайт может открыть сокет к вашему серверу, и
  браузер пришлёт cookie. Защита — проверка заголовка `Origin` на сервере (`server/index.ts`).

## Коды закрытия

У закрытия есть код — по нему клиент понимает, что произошло.

| Код | Значение |
| --- | --- |
| 1000 | обычное закрытие |
| 1001 | сторона «уходит» (закрыли вкладку, сервер останавливается) |
| 1006 | **обрыв**: соединение пропало без кадра закрытия. Сервер его не отправляет — этот код ставит сам браузер |
| 1008, 1009, 1011 | нарушение правил, слишком большое сообщение, ошибка сервера |
| 4000–4999 | **диапазон приложений** — придумывайте свои |

Свои коды «Прилавка» (`CLOSE` в `protocol.ts`):

| Код | Значение | Переподключаться? |
| --- | --- | --- |
| 4000 | сервер перезапускается | да |
| 4401 | токен не принят | **нет** — нужен вход |
| 4408 | клиент не прислал `hello` | да |
| 4409 | клиент долго молчал | да |
| 4426 | версия протокола не поддерживается | **нет** — нужно обновить страницу |
| 4999 | закрыто самим клиентом (нет pong, таймаут) | да |

Из браузера в `close()` можно передать только 1000 или 3000–4999.

## Ping и pong: два разных

В самом протоколе WebSocket есть служебные кадры ping/pong. Сервер на `ws` умеет их слать,
браузер отвечает сам. Но **из JavaScript в браузере их не отправить и не увидеть**. Поэтому
клиент, который хочет проверять связь, шлёт обычное сообщение `{"t":"ping"}` — это
«прикладной» ping (глава 04).

## Когда нужен не WebSocket

| Способ | Как работает | Когда брать |
| --- | --- | --- |
| **Polling** | `fetch` раз в N секунд | данные меняются редко, задержка в 10–30 с не страшна. Самый простой и надёжный |
| **Long polling** | сервер держит запрос, пока не появится новость | нужна совместимость со всем на свете |
| **SSE** (`EventSource`) | один долгий HTTP-ответ, сервер пишет в него события | **только сервер → клиент**: ленты, уведомления, прогресс. Переподключение и докачка (`Last-Event-ID`) встроены в браузер |
| **WebSocket** | двусторонний канал | чат, совместное редактирование, присутствие, игры — когда клиент тоже шлёт часто |
| **WebTransport** | поверх HTTP/3 | нужна доставка без порядка (игры, видео); пока редкость |

Честный вывод про «Прилавок»: лента заказов и метрики отлично работали бы на SSE. WebSocket
оправдан заметками и присутствием — там клиент активно пишет. В настоящем проекте сначала
спросите себя, не хватит ли SSE или polling: их сопровождать проще.

## Посмотреть глазами

- **Экран «Соединение»** — журнал кадров в самом приложении.
- **DevTools → Network → фильтр WS** → выбрать соединение → вкладка **Messages**: каждый
  кадр, направление, размер, время. Работает в режиме настоящего сервера
  (`npm run dev:real`); в мок-режиме сети нет — смотрите журнал в приложении.
- Вкладка **Headers** того же соединения — запрос `Upgrade` и ответ `101`.
