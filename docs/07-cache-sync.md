# 07. Сокет и интерфейс

Файлы: `src/realtime/sync.ts`, `live.ts`, `hooks.ts`, `src/api/mutations.ts`.

## Один источник правды

Экраны читают данные из кэша TanStack Query (глава 08). Если событие сокета обновляет
что-то в обход кэша — например, локальный `useState` — получаются две версии правды:
список показывает одно, карточка другое.

Правило: **событие сокета меняет кэш; экраны читают кэш**. Ни один компонент не знает,
откуда пришло обновление.

```
HTTP-ответ ──────────┐
                     ├──▶ кэш запросов ──▶ все экраны, которые эти данные показывают
событие сокета ──────┘
        (sync.ts)
```

## Три способа отреагировать на событие

| Способ | Когда | Пример |
| --- | --- | --- |
| **Поправить кэш** (`setQueryData`) | в событии есть всё нужное | статус заказа, заметка, остаток товара |
| **Пометить устаревшим** (`invalidateQueries`) | событие говорит «что-то изменилось», а пересчитать сами не можем | статистика дашборда |
| **Сообщить человеку** | данные нельзя поправить на месте, а менять экран под рукой нельзя | новые заказы в отфильтрованном списке |

### 1. Поправить кэш

```ts
client.on('order.updated', (event) => {
  queryClient.setQueryData<OrderDetail>(keys.order(event.id), (detail) =>
    detail && detail.order.version < event.version ? { …новый статус, версия, запись истории… } : detail)

  queryClient.setQueriesData<Page<OrderRow>>({ queryKey: keys.orderLists }, (page) => …)
})
```

- `setQueryData` с функцией: если заказа в кэше нет (`detail === undefined`), ничего не
  создаём — его никто не смотрит.
- `setQueriesData` (множественное число) правит **все** запросы, чей ключ начинается с
  `['orders', 'list']`: строку на любой закэшированной странице и при любых фильтрах.
- Новый объект вместо изменения старого: Query сравнивает по ссылке.

Запросов к серверу — ноль.

### 2. Пометить устаревшим

Выручка за 30 дней зависит от всех заказов — пересчитать её по одному событию нельзя.
`invalidateQueries({ queryKey: keys.stats })`: если дашборд на экране — перезапросится
сейчас, если нет — при следующем показе.

Не на каждое событие, а не чаще раза в 10 секунд (throttle):

```ts
statsTimer ??= setTimeout(() => { statsTimer = null; invalidate() }, 10_000)
```

`??=` — «назначить, только если пусто»: пока таймер идёт, новые события его не перезапускают.

### 3. Сообщить человеку

Новый заказ и список с фильтром «только отменённые, страница 3, сортировка по сумме».
Попадает ли он в этот список? На какую страницу? Клиент этого не знает. А если бы и знал —
вставлять строку в таблицу, в которую человек целится мышью, нельзя: всё съедет.

Поэтому событие копится в счётчике (`live.fresh`), а над таблицей появляется: «Пока вы
здесь, пришло 3 новых заказа — Показать». Тот же счётчик — бейдж в боковом меню.

По кнопке «Показать» список перезапрашивается и встаёт на «свежие сверху», а пришедшие
заказы **отмечаются** полоской слева с подписью «3 новых заказа отмечены в таблице». Без
отметки человек нажимает кнопку и не понимает, что изменилось: строки просто сдвинулись.
Если часть новых заказов не подходит под включённые фильтры — об этом сказано отдельно, с
кнопкой «Сбросить фильтры».

## Версии: защита от двух гонок

У заказа есть `version` — растёт на 1 при каждом изменении. Событие применяется, только
если оно новее кэша: `current.version < event.version`.

**Гонка 1: своя же правка приходит дважды.** Я сменил статус по HTTP. Сервер ответил мне —
и разослал событие всем, включая меня. Без проверки в истории заказа появились бы две
одинаковые записи. Событие и HTTP-ответ могут прийти в любом порядке:

| Порядок | Что происходит |
| --- | --- |
| ответ (v2) → событие (v2) | ответ записан; событие не новее — пропущено |
| событие (v2) → ответ (v2) | событие применено; ответ заменяет заказ целиком (он полнее) |

**Гонка 2: события пришли не по порядку** (после досылки, из разных источников). Старое
событие не откатит заказ назад. Тест: «запоздавшее старое событие не откатывает заказ».

Та же версия служит серверу: `PATCH /orders/:id {status, version}`. Версия устарела —
ответ 409: «заказ уже изменил кто-то другой». Это **оптимистичная блокировка**: не запрещаем
двоим открыть заказ, но не даём молча затереть чужую правку.

## Оптимистичное обновление

Обычно: нажал → ждёшь → обновилось. Оптимистично: нажал → обновилось сразу → запрос идёт
следом. Если сервер откажет — возвращаем как было.

`useOrderStatus` в `mutations.ts`:

```ts
onMutate: async ({ status }) => {
  await queryClient.cancelQueries({ queryKey: key })          // 1. чтобы летящий запрос не затёр
  const previous = queryClient.getQueryData(key)              // 2. запомнить, как было
  queryClient.setQueryData(key, { …previous, order: { …, status } })   // 3. показать сразу
  return { previous }
},
onError: (error, input, context) => {
  queryClient.setQueryData(key, context.previous)             // 4. откат
  toast.error('Статус не изменён', { description: error.message })
},
onSuccess: (order) => queryClient.setQueryData(key, …order…)  // 5. настоящий ответ
```

Тонкость: в шаге 3 версия **не увеличивается**. Если бы мы написали `version + 1`, событие
сокета о нашей же правке было бы «не новее» и отброшено — а с ним и запись истории, пока не
придёт HTTP-ответ.

### Оптимистичная заметка — через сокет

`useAddNote`: заметка показывается сразу с временным id = `clientId`, бледной, с подписью
«отправляется…». Дальше два события в любом порядке:

- `ack` на запрос → `onSuccess` заменяет временную заметку настоящей;
- событие `note.added` с тем же `clientId` → `sync.ts` находит временную и заменяет.

Оба обработчика проверяют «а нет ли уже заметки с таким id» — кто бы ни пришёл первым,
заметка одна. Коллегам приходит только событие (у них `clientId` ни с чем не совпадёт —
заметка просто добавится).

## Не всё — кэш запросов

«Сейчас на сайте 42» — не ответ на HTTP-запрос. Такому состоянию место в отдельном
хранилище (`live.ts`): метрики, лента новых заказов, счётчики, отметки «строку только что
изменили». Это 25 строк в `lib/store.ts` и `useSyncExternalStore`.

## Хуки

```ts
useChannel(CHANNELS.metrics)              // подписка, пока компонент на экране
useRealtimeEvent('presence', (data, frame) => { … })   // реакция на событие
const { status, latency } = useRealtimeStatus()        // состояние соединения
```

**`useChannel`** — три строки:

```ts
useEffect(() => (channel ? realtime.subscribe(channel) : undefined), [channel])
```

`subscribe` возвращает функцию отписки, `useEffect` вызовет её при размонтировании. Подписка
не может «утечь».

**Счётчик слушателей.** Канал `orders` слушают каркас приложения и таблица. Серверу уходит
один `sub` при первом слушателе и один `unsub`, когда ушёл последний.

**Отложенная отписка.** При переходе «список товаров → товар» первый экран отписывается от
`products`, второй тут же подписывается. Серверу летели бы `unsub` + `sub`, а между ними
можно потерять событие. Клиент ждёт 300 мс перед `unsub` — новый слушатель успевает прийти
(тест «быстрая переподписка не доходит до сервера»). Заодно это гасит двойной запуск
эффектов в React StrictMode.

**`useSyncExternalStore`** — штатный способ React читать то, что живёт вне его (сокет,
хранилище). Требование: `getSnapshot` должен возвращать **тот же объект**, пока ничего не
изменилось. Иначе — бесконечная перерисовка. Поэтому `RealtimeClient.patch` сначала
сравнивает значения и только при настоящем изменении создаёт новый снимок.

**`useEffectEvent`** в `useRealtimeEvent`: обработчик видит свежие пропсы и состояние, но
эффект не переподписывается на каждый рендер.

## Подсветка изменений

Строка, которую изменило событие, на секунду подсвечивается. Приём:

```tsx
<TableRow key={`${row.id}:${touched[row.id] ?? 0}`} className={isRecent(touched[row.id]) && 'flash-row'} />
```

Метка времени в `key`: изменилась — React создаёт элемент заново — CSS-анимация проигрывается
снова. Без JavaScript-анимаций.

## Доступность живых данных

- Лента заметок — `aria-live="polite"`: скринридер зачитает новую.
- Метрики, меняющиеся каждые 2 секунды, — **без** `aria-live`: иначе чтение не остановится.
- Баннер о новых заказах и полоса «нет связи» — `role="status"`.
- Анимации отключаются при `prefers-reduced-motion`.
